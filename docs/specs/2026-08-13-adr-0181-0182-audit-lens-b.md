## F1 (MAJOR/CRITICAL) — "breaking for authoring, not for loading" is a false dichotomy: the YAML path re-validates at every parse
ADR-0182 Consequences; spec §3 Consequences.
`definition.NewLoader` → `build/build.go:64` → `model.ParseYAML` → `DefinitionLoader.Build()` →
`builder.go:133 Validate(&def)`. YAML is one of the two documented authoring forms. A consumer
that keeps YAML definitions on disk and parses them at PROCESS START (the natural library
deployment) gets the new rejection at BOOT, not in CI. Blast radius is "CI + every boot that
re-parses YAML", not "CI".
FIX: replace the sentence with the precise closed set — "`Validate` has exactly one production
caller, `definitionCore.build()`; it is reached by `definition.NewBuilder(...).Build()` and by
`definition.NewLoader(yaml).Build()`. Definitions already stored in `wrkflw_definitions` are
`json.Unmarshal`ed with no validation (`store/definitions.go` GetDefinition/Lookup) and keep
loading. A consumer that parses YAML at startup will fail at startup." Add a migration note.

## F2 (CRITICAL) — `next_run = <zero>` equality misses the very rows it targets on SQLite (ADR-0151 encoding change)
ADR-0181 Decision; spec §2 Decision; plan P1 step 2.
`timeArg` (store/time_codec.go:39) formats SQLite timestamps with `textTimeLayout`
(fixed nine-digit fraction, ADR-0151). Rows written by an OLDER binary used the trimmed
`time.RFC3339Nano` form — `parseTimeText` tolerates both on READ, but an `=` predicate does not.
EXECUTED:
```
PROBE fixed-width = "0001-01-01T00:00:00.000000000Z"
PROBE RFC3339Nano = "0001-01-01T00:00:00Z"
PROBE equal       = false
```
Orphans are by construction OLD rows (pre-ADR-0176), i.e. exactly the population most likely to
carry the pre-ADR-0151 encoding. The sweep would report 0 reclaimed and look correct.
FIX: do not use equality on the timestamp. Use a bound below any legitimate value, e.g.
`trigger_kind IN (<recurring>) AND next_run < ?` bound with a sentinel epoch (`1970-01-01`), which
is correct under BOTH text encodings (lexicographic order is preserved for the year field) and on
Postgres/MySQL. State the chosen sentinel in the ADR. Add a test seeding an orphan in the TRIMMED
encoding and asserting it is reclaimed — that test fails against the `=` design.

## F3 (CRITICAL) — ADR-0181's cross-dialect ASSUMPTION contradicts an ALREADY-MEASURED fact: MySQL cannot hold a zero-`next_run` row
ADR-0181 Context (L36-38); spec §2; plan Verification-checklist bullet 6.
ADR-0176 measurements §4 (in-repo, `docs/specs/2026-08-13-adr-0176-measurements.md:70-88`) MEASURED:
postgres accepted, sqlite accepted, **mysql REJECTED** — `Error 1292 (22007): Incorrect datetime
value: '0000-00-00' for column 'next_run'`. So the orphan population on MySQL is provably EMPTY.
Consequences the bundle misses:
1. The assumption "the same 0-of-4 result holds on Postgres and MySQL" is not merely unverified —
   for MySQL it is refuted by an in-bundle-adjacent measurement. It would be 0-of-0.
2. The plan's checklist item "the same 0-of-4 baseline and the same reclamation on Postgres and
   MySQL" is UNRUNNABLE as written on MySQL: the seeding step errors 1292. An implementer will
   discover this only after wiring Docker.
3. This is a *population* difference, not the *implementation-uniformity* question ADR-0181 frames
   it as ("one implementation, not one per dialect").
FIX: replace the assumption with the measured fact + a narrowed one:
"MEASURED (ADR-0176 §4): MySQL rejects a zero `next_run` at insert under strict mode, so MySQL has
no orphan population and the sweep is a no-op there. ASSUMPTION (unverified — needs Docker): the
Postgres reclamation matches the SQLite result." Change the plan's Docker item to
"Postgres only; MySQL asserted to have zero seedable orphans (seeding raises 1292)".
⚠ Also record the non-strict-`sql_mode` caveat: a MySQL deployment WITHOUT
STRICT_TRANS_TABLES/NO_ZERO_DATE stores `'0000-00-00 00:00:00'` instead of erroring, which is NOT
`0001-01-01` — another reason the predicate must not be an equality on the Go zero time (see F2).

## F4 (MAJOR) — the cross-check test (ADR-0182's ONLY drift mitigation) needs a conversion that does not exist outside `runtime`, so it silently becomes a THIRD copy
ADR-0182 Consequences (L65-69); spec §3; plan P2 step 4.
`scheduler.Trigger.Next` takes a `scheduler.Trigger`. The only `schedule.TriggerSpec → scheduler.Trigger`
converter is `convertTrigger`, **unexported**, in `runtime/timerops.go:44`. `package model_test`
cannot reach it. So the cross-check test must hand-roll its own conversion — a third source of
truth, written by the same author, in the same session, from the same mental model as the
predicate. Drift in the CONVERSION is then invisible to the test that exists to detect drift.
FIX: either (a) state explicitly in ADR-0182 that the cross-check test carries a test-local
conversion and that its correctness is NOT established by the cross-check (list it as a known
blind spot), or (b) build the cross-check as a `runtime`-package test where the real
`convertTrigger` is in scope and the predicate is imported from `model` — that closes the blind
spot at the cost of the test living beside the scheduler dependency it must move with anyway.

## F5 (CRITICAL) — ADR-0181 as planned ships DEAD CODE: no public route exists to the new sweep on ANY dialect
ADR-0181 Decision + Consequences bullet 1; spec §2 Consequences; plan P1 step 4.
Verified: ALL THREE public constructors return the **interface**, not the concrete type —
`persistence.NewPruner` (pruner.go:62, Postgres), `persistence.NewMySQLPruner` (mysql.go:369),
`persistence.NewSQLitePruner` (sqlite.go:317). `internal/persistence/store` is `internal/` and
cannot be imported by a consumer. So after P1 there is:
- no method on the public interface,
- no public constructor returning a type that carries the method,
- no in-repo caller (the plan builds none),
- no documented type-assertion escape (an anonymous `interface{ PruneNeverDue... }` assertion does
  work against the dynamic `*store.Pruner`, but nothing says so).
The ADR's phrasing "a consumer wiring only the public interface cannot reach it" understates this:
there is no consumer wiring that CAN reach it. The spec's "an operator running the store's
maintenance path" names a path that does not exist outside the module.
FIX: pick one and record it. (a) Add the method to `persistence.Pruner` — it is a source-breaking
change for anyone implementing the interface, which is the honest cost, and note the repo already
ships breaking changes (ADR-0174). (b) Keep the interface and add a public **optional-capability
interface** `persistence.NeverDueTimerReclaimer` plus a documented type assertion — non-breaking
and reachable. (c) Explicitly scope ADR-0181 to internal maintenance and say the operator route is
deferred — but then the Positive consequence "an operator can reclaim rows that today require
manual SQL" is FALSE and must be deleted.

## F6 (MAJOR) — an irreversible delete with no record: the sweep destroys the only timer-side evidence of a permanently parked instance, and nothing is logged
ADR-0181 Consequences (last bullet); spec §2; plan P1 (no observability step).
The orphan row is the artefact of an instance that armed a never-due timer and is parked forever.
Deleting it removes the row from `ListArmed`/`Stats` — the timer-side diagnostics — while the
instance stays parked. Neither ADR nor plan prescribes a log line, metric, or event for what was
deleted, and the delete is irreversible by the ADR's own admission. Compare ADR-0175, which shipped
an operator escape precisely because silently-stalled work is the failure mode this repo cares about.
FIX: prescribe (i) an `slog` line at the sweep naming instance_id/timer_id/def_id per deleted row
(or at minimum the count and the distinct instance ids), and (ii) a documented note in the ADR that
reclaiming the row does NOT unpark the instance — the instance remains stuck and must be handled
separately. Add a plan step + test asserting the deleted identities are reported.

## F7 (MAJOR) — ADR-0181 promises `Stats.NextFireAt` is "freed"; the plan verifies no such thing
ADR-0181 Consequences, Positive (L57-58) vs plan P1 (tests are reclaim-count + ADR-0134 guard only).
`Stats.NextFireAt` pinned at `0001-01-01` is cited (ADR-0176 measurements §4 FINDING B) as a
motivating symptom, and the ADR states it is fixed. No prescribed test observes `Stats` before and
after the sweep. Per rule #11 this is the ADR-0162 zombie-scope shape: a promise nobody builds.
FIX: add to plan P1 a test — seed one orphan + one healthy future row, assert
`Stats().NextFireAt == 0001-01-01` BEFORE and `== <future>` AFTER the sweep. State what makes it
fail today (the sweep does not exist; and it fails again if the predicate is wrong per F2).

## F8 (CRITICAL) — ADR-0182's rejection list is UNSOUND in one direction and UNDER-REACHING in the other. EXECUTED.
ADR-0182 Decision (L37-41); spec §3 Decision; plan P2 step 1.
Probe over `scheduler.Trigger.Next` at three anchors (2026-02-01, 2026-08-15, 2027-12-31):
```
Every(0)            ok=false ok=false ok=false
Daily(0)            ok=false ok=false ok=false
Weekly(0,Mon)       ok=false ok=false ok=false
EveryRandom(5,5)    ok=false ok=false ok=false      <- min==max IS never-due; the ADR's ">=" is right
EveryRandom(10,5)   ok=false ok=false ok=false
Cron(bogus)         ok=false ok=false ok=false
Cron("0 0 30 2 *")  ok=false ok=false ok=false      <- ANCHOR-INDEPENDENTLY never-due, PARSEABLE
Daily(1,Hour=25)    ok=false ok=false ok=false
Weekly(1,Weekday=9) ok=TRUE  ok=TRUE  ok=TRUE       <- fires Tue; wraps mod 7
Monthly(1,[32])     ok=false ok=false ok=false
Monthly(12,[31])    ok=false ok=TRUE  ok=TRUE       <- anchor-dependent, correctly excluded
Daily(1,Hour=9)     ok=TRUE  ok=TRUE  ok=TRUE       (control)
```
(a) **UNSOUND over-reach.** ADR-0182 lists "out-of-range … weekday …" among the classes to
    reject. `Weekly(1, []time.Weekday{9}, 09:00)` is measurably DUE at every anchor tested
    (2026-02-10, 2026-08-18, 2028-01-04) — the weekday wraps mod 7. Rejecting it violates the
    ADR's OWN soundness constraint (§1) and is the ADR-0165 inverted-predicate shape verbatim.
(b) **UNDER-REACH on the delivery's own headline example.** `Cron("0 0 30 2 *")` — cited in
    ADR-0182 Context and spec §3 as the thing that "validates clean today" — is parseable, so the
    enumerated list ("an unparseable cron") does NOT catch it, yet it is never-due at every anchor
    (Feb 30 does not exist). The gate ships without catching the example that motivates it.
FIX: (a) DELETE "weekday" from the rejection list and add a soundness-guard test alongside the
`Monthly(12,[31])` one: `Weekly(1,[Weekday(9)])` must NOT be rejected. (b) Either add a
never-due-cron check (day-of-month/month combination impossible, e.g. 30/31 February) and say so,
or state explicitly that parseable-but-impossible cron is OUT OF SCOPE and stop citing
`Cron("0 0 30 2 *")` as the motivating example. Whichever is chosen, re-derive the whole
enumeration by execution and paste this table into the spec.

## F9 (CRITICAL) — "out-of-range day-of-month" is unsound for NEGATIVE days, and the interval-0 enumeration is incomplete. EXECUTED.
ADR-0182 Decision (L37-41); spec §3; plan P2 step 1.
```
Monthly(0,[15])     ok=false ok=false ok=false   <- never-due, NOT in the ADR's interval-0 list
Every(-1s)          ok=false ok=false ok=false   <- never-due, NOT listed (list says Every(0) only)
Cron("")            ok=false ok=false ok=false
Daily(1,Minute=61)  ok=false ok=false ok=false
Daily(1,Second=61)  ok=false ok=false ok=false
Monthly(1,[0])      ok=false ok=false ok=false
Monthly(1,[-1])     ok=TRUE  ok=TRUE  ok=TRUE    <- 2026-02-28 / 2026-08-31 / 2028-01-31: NEGATIVE
                                                    day == last-day-of-month. Rejecting it as
                                                    "out of range" is UNSOUND.
Monthly(1,[])       ok=TRUE  ok=TRUE  ok=TRUE
```
The ADR's enumeration is stated as a closed list ("rejecting only … `Every(0)`, `Daily(0)`,
`Weekly(0, …)`, `EveryRandom(min >= max)`, an unparseable cron, and out-of-range day-of-month /
weekday / clock fields") and it is wrong on four counts: `Monthly(0,…)` missing, negative
durations missing, weekday must come out (F8), and negative day-of-month must be EXCLUDED from
"out of range".
FIX: replace the prose list with a table of the EXECUTED verdicts (both probe tables above),
stating for each row `never-due at every anchor: yes/no`. Define the day-of-month rule precisely as
`d == 0 || d > 31 || d < -31` (negatives are last-N-days and are legal). Add
`Monthly(1,[-1])` to the soundness-guard test beside `Monthly(12,[31])`.

## F11 (MAJOR) — the prescribed P1 verification command needs Docker, and the conformance home forces an impossible MySQL case
plan P1 Verify (`go test -count=1 -run '^TestPrune' -v ./internal/persistence/store/`) and the
plan's ⚠ "P1 needs Docker only for its cross-dialect claim".
`-run '^TestPrune'` matches `TestPruner` (`pruner_conformance_test.go:30`), which calls

⚠ Note also CLAUDE.md pitfall #5: `-run` on a name that does not exist EXITS 0, so a filtered

## F13 (MINOR) — the sweep's concurrency safety is undefined
No document states how the sweep executes. `PruneTimers` (pruner.go:190-214) is a SINGLE
`DELETE … WHERE` statement, which re-evaluates the predicate atomically and is therefore safe
against a concurrent re-arm of the same (instance_id, timer_id). A batched/keyset variant
(SELECT ids, then DELETE by PK) would introduce a TOCTOU: a row re-armed with a valid `next_run`
between the SELECT and the DELETE would be destroyed.
FIX: state in ADR-0181 Decision that the sweep is a single-statement `DELETE`, and say why
(atomic predicate re-evaluation vs. a concurrent `upsertTimer`).

## F14 (MINOR) — the fixed-corpus mitigation cannot detect drift, and a property test is feasible
ADR-0182 Consequences (L65-69); spec §3; plan P2 step 4.
A fixed corpus only ever re-checks inputs already agreed on. Realistic drift sources: gocron is
HARD-PINNED at v2.22.0 (ADR-0135), so the likely drift is a change to in-repo `scheduler/trigger.go`
`Next` (`scheduler/trigger.go:245`) — e.g. the weekday-wrap or negative-day behaviour measured in
F8/F9 being "fixed". A corpus written today would still pass while the predicate and `Next`
diverged on any input outside it.
The probes above show `Next` is DETERMINISTIC for every kind including `EveryRandom` (documented at
`scheduler/trigger.go:229` as reporting the earliest bound), so a `go test -fuzz` / property
cross-check over generated `TriggerSpec`s comparing only the `ok` boolean IS feasible.
FIX: keep the corpus as the regression floor and add a seeded property test (fixed anchors ×
randomised interval/day/weekday/clock fields) asserting predicate-verdict == `!ok`. State the
gocron pin as the reason external drift is bounded — that is a real mitigation the ADR does not claim.
