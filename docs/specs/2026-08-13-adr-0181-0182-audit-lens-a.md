### F1 (MAJOR) — the equality predicate misses SQLite orphans in the pre-ADR-0151 encoding
ADR-0181 "Decision"; spec §2 "Decision"; plan P1 step 2. `next_run = <zero>` is a TEXT equality on
SQLite. `internal/persistence/store/time_codec.go` `parseTimeText` doc states in-repo that
"Values written with the previous trimmed encoding remain readable" — i.e. the repo asserts legacy
trimmed rows exist. Executed: a zero next_run written with the old trimmed layout
("0001-01-01T00:00:00Z") is NOT matched (deleted=4, orphan-legacy survived); the `<` threshold
variant caught it (deleted=1) and still spared armed-future.
FIX: predicate `next_run < <threshold> AND recurring` with a threshold far below any real arming
instant (e.g. year 1000 / `time.Date(1000,1,1,...)`), not `= <zero>`. Add the trimmed-encoding
orphan to the P1 fixture — otherwise the prescribed test cannot fail on this axis.

### F2 (MAJOR, partly ASSUMPTION) — the "dialect-neutral" claim is unsafe on MySQL: DATETIME range
ADR-0181 Context: "the SQL is dialect-neutral and only `Rebind`/`timeArg` differ". Source-verified:
`internal/persistence/store/migrations/mysql/0001_init.sql:95` declares `next_run DATETIME(6) NOT NULL`.
MySQL's DATETIME range is '1000-01-01' .. '9999-12-31' — the Go zero time (year 0001) is OUT OF
RANGE, so a zero next_run cannot round-trip as year 1 on MySQL; it is either rejected under strict
mode or coerced (classically to the zero-date '0000-00-00'). Either way `next_run = <zero-time>`
cannot be assumed to match. `ASSUMPTION (unverified — needs Docker)` that coercion, not rejection,
is what happened historically. This is *not* covered by the ADR's existing Docker caveat, which
assumes only that the result generalises.
FIX: state the DATETIME-range hazard explicitly in ADR-0181; make the threshold form (F1) the
decision, since `next_run < '1000-01-01'` matches both a coerced zero-date and a year-1 value on
Postgres; require the Docker run to assert reclamation, not merely the 0-of-4 baseline.

### F3 (CRITICAL) — "out-of-range weekday" in the reject list is UNSOUND
ADR-0182 Decision; spec §3 Decision; plan P2 step 1. Executed: `Weekly(1,[time.Weekday(9)])` and
`Weekly(1,[time.Weekday(7)])` are DUE at every anchor probed. `scheduler/trigger.go` `Weekly` doc
says so deliberately: "A weekday outside Sunday–Saturday is likewise accepted and NOT normalised
… time.Weekday(8) fires eight days after a Sunday arm". A gate rejecting them refuses definitions
that fire today — the exact unsoundness §1 forbids, and it also breaks the ADR-0176 reconciliation.
Only the ALL-NEGATIVE weekday set is never-due (`Weekly(1,[Weekday(-1)])` → never at every anchor).
FIX: delete "out-of-range weekday" from the reject list in ADR-0182 Decision, spec §3, plan P2.1;
replace with "a Weekly whose weekdays are ALL negative" — the branch Next actually has. Add
`Weekly(1,[Weekday(7)])` and `Weekly(1,[Weekday(9)])` to the §6.3 soundness-guard corpus next to
`Monthly(12,[31])`.

### F4 (CRITICAL) — the reject corpus (P2.1) and the cross-check corpus (P2.4) contradict each other
Plan steps P2.1 vs P2.4; spec §6.2 vs §6.4. P2.1 asserts the whole reject list errors at
`model.Validate`; P2.4 asserts predicate verdict == `Trigger.Next` verdict. For out-of-range
weekday these are mutually unsatisfiable (F3). The bundle does not say which wins, so an
implementer resolves it by whichever test they write first — and if they choose a cross-check
corpus that omits weekdays, the drift the whole design rests on goes undetected.
FIX: state in the plan that **the cross-check corpus is the SAME corpus** as the reject/accept
corpus (one table, two assertions per row), and that `Trigger.Next` is the arbiter — any
disagreement is a defect in the predicate, never a reason to shrink the corpus.

### F5 (MAJOR) — `Monthly(0, …)` is missing from the reject list
ADR-0182 Decision names `Every(0)`, `Daily(0)`, `Weekly(0,…)` but NOT `Monthly(0,…)`. Executed:
`Monthly(1,[1])`-shaped spec with interval 0 → never-due at every anchor (`Trigger.Next` doc:
"a zero interval for [Daily], [Weekly], or [Monthly]"). Enumeration rot: three of the four zero-
interval kinds are named. Also `Every(-1s)` (negative, not just zero) and `EveryRandom(min<=0)`
are never-due and unnamed.
FIX: restate as closed branches of `Trigger.Next`: non-positive duration for `Every`; non-positive
min OR min>=max for `EveryRandom`; zero interval for `Daily`/`Weekly`/**`Monthly`**; unparseable or
unmatched cron; all-negative `Weekly` weekdays; out-of-range day-of-month / clock.

### F6 (MAJOR) — "out-of-range day-of-month" is a trap: negative days are LEGAL
ADR-0182 Decision; spec §3. Executed: `Monthly(1,[-1])` is DUE at every anchor (2026-02-28,
2026-08-31, 2026-06-30) — `Monthly`'s doc: "A NEGATIVE day counts back from the end of each
candidate month". `Monthly(1,[0])`, `[32]`, `[-32]` are never-due. A predicate written as
`day < 1 || day > 31` — the obvious reading of "out-of-range" — is UNSOUND.
FIX: spell the legal range in ADR-0182 and the plan: reject only `day == 0 || day > 31 || day < -31`
(matching the scheduler's own arm-time rule quoted in `Monthly`'s doc). Put `Monthly(1,[-1])` in
the §6.3 must-not-reject corpus.

### F7 (MAJOR) — shipped `scheduler/trigger.go` doc comments contradict the executed behaviour
Three statements in `scheduler/trigger.go` claim `EveryRandom` bounds are unvalidated:
(a) `EveryRandom` constructor doc — "a min greater than max is not rejected by this constructor …
Next always uses min as the earliest bound regardless"; (b) `Next`'s ok=false bullet list — names
only "a non-positive min for [EveryRandom]"; (c) `Next`'s per-constructor paragraph — "bounds are
not validated here (e.g. min>max)". The code (`case triggerEveryRandom`) does `if t.min <= 0 ||
t.min >= t.max { return zero, false }`, and the probe confirms EveryRandom(10s,5s) and (5s,5s) are
never-due at every anchor. Doc rot left by ADR-0176's `/code-review` fix.
FIX: widen plan phase P3 (currently only `runtime/timerops.go`'s `neverDueNextRun` comment) to
sweep these three statements. They are load-bearing for THIS bundle: ADR-0182 cites the
`EveryRandom` reject on them, and spec §4.4 restates the fix as "min>max" when the code closes
"min>=max".

### F9 (MAJOR) — the gate does not cover deadline triggers, and "already rejected" is only half true
ADR-0182 Decision ("Skip the recurring-`DeadlineTimer` half: `validate.go:656` already rejects
it"); spec §3. Executed: a **never-due ONE-SHOT** deadline `schedule.At(time.Time{})` on a nested
UserTask → `model.Validate` returns `<nil>`, while `scheduler.At(time.Time{}).Next(...)` reports
**ok=false** — genuinely never-due at every anchor, and anchor-INDEPENDENT, i.e. squarely in the
gate's stated scope. The existing rule only catches `Recurring()` deadlines, and the new gate reads
`toWire(n).TimerTrigger`, a wire field distinct from `DeadlineTrigger` (`node_wire.go:42-43`), so
it never sees a deadline at all.

`DeadlineOf` accessor already exists and is already used inside `validateStructure`), or amend
ADR-0182 and spec §3 to say explicitly that deadline triggers are OUT OF SCOPE and that a never-due
one-shot deadline still reaches the arm guard only. Do not leave "already rejects it" unqualified.

### ⚠ F9 RETRACTED — my own analogous-case error, caught by executing the real path
`runtime/timerops.go:44` `convertTrigger`, KindOneTime branch: `if at, ok := t.AbsTime(); ok
{ return scheduler.At(at) }` else `d,_ := t.Duration(); return scheduler.After(d)`.
`schedule.At(time.Time{})` has `AbsTime()` ok=FALSE (guarded on `!s.at.IsZero()`), so it converts

(every form converts to `At(non-zero)` or `After(d)`, both DUE), KindExpr (engine-resolved;

Replacement finding, MINOR: record that executed reason in spec §3, otherwise the next reader

### F10 (CRITICAL) — the cross-check test cannot exercise the real conversion, so it can pass while production diverges
Plan P2.4; spec §6.4; ADR-0182 Consequences. The arm-time path is
`schedule.TriggerSpec --convertTrigger--> scheduler.Trigger --Next--> ok`. `convertTrigger` is
**unexported in package `runtime`**, so a test in `package model_test` cannot call it; it must
hand-build a `scheduler.Trigger` from the spec — i.e. re-implement `convertTrigger`. That is a
THIRD copy of the same mapping, and the divergence it hides is real and already demonstrated
above: `schedule.At(time.Time{})` maps to `scheduler.After(0)` (DUE) via `convertTrigger` but to
`scheduler.At(zero)` (NEVER-DUE) if built naively. A cross-check built the naive way asserts
agreement between two things neither of which is what production runs.
FIX: make the conversion reachable — export a thin `runtime.ConvertTrigger` (or move the mapping to
a package both can import) and require P2.4 to drive the corpus through it, so the chain under test
is exactly the production chain. Failing that, ADR-0182 must state that the cross-check covers the
predicate vs `Trigger.Next` ONLY, and that `convertTrigger` is an unverified third copy.
