# Audit round 3 — ADR-0186 — FAILURE-MODES lens

Worktree: wt/failure-modes @ 6cddb7b1. Bundle verified present (step 0 OK).

### F1 — `MaxBodyBytes = 0` (the documented "unbounded" opt-out, and the mode the migration story mandates) means "reject EVERY non-empty body with 413" if passed straight to the prescribed mechanism
**Severity:** Critical
**Bundle says:** ADR-0186 D1 — *"`httpcore.CustomizeConfig.MaxBodyBytes`, default **1 MiB**, `0` = unbounded (the explicit opt-out), honoured by every adapter through its own idiom: `http.MaxBytesReader` for stdlib; the same wrapper applied to `c.Request.Body` … for gin; and a `len(c.BodyRaw())` pre-check for fiber"*. Plan §3 phase 4 repeats the mechanism verbatim. ADR-0186 D1 "Migration and discoverability — corrected": *"**set `MaxBodyBytes = 0`, observe the distribution, then choose a cap**"*. Spec §4.1: *"`0` = unbounded"*.
**The case it misses:** `http.MaxBytesReader(w, body, 0)` does not mean unbounded — it means a limit of zero, and the **first** `Read` of a non-empty body fails. The bundle never says "the adapter must branch and skip installing the reader when the cap is 0", and no prescribed test in any phase exercises `MaxBodyBytes = 0`. The identical inversion exists on fiber: `len(c.BodyRaw()) > 0` rejects every non-empty body. So the very configuration the ADR tells operators to run in production *to collect the histogram* is the configuration that 413s every request.
**Evidence:** executed, throwaway module, `go test -run TestMaxBytesReaderZero -v` → `EXIT=0`:
```
limit=0        err=http: request body too large isMaxBytes=true decoded=map[]
limit=-1       err=http: request body too large isMaxBytes=true decoded=map[]
limit=1048576  err=<nil>                        isMaxBytes=false decoded=map[a:1]
```
(`-1` behaves identically — `MaxBytesReader` clamps `n < 0` to `0`, so "use a negative to disable" is also not an escape.)
**Consequence:** an operator following the ADR's own migration procedure takes a **100% outage on every write route** — all 39 decode sites return 413. Worse, the failure is *silent in review*: the naive implementation `http.MaxBytesReader(w, r.Body, cfg.MaxBodyBytes)` is exactly what the ADR's prose describes, compiles, and passes every prescribed test (all of which run with a non-zero cap).
**Fix:** (a) state the branch explicitly in D1 and in plan phase 4: *"when `MaxBodyBytes <= 0` the adapter installs no reader and performs no pre-check"*; (b) add a mandatory phase-4 test row per adapter — `TestZeroMaxBodyBytesAcceptsALargeBody`, sending a body far above 1 MiB with `MaxBodyBytes = 0` and asserting 2xx — with the falsifier stated: *it fails against an implementation that passes 0 to `MaxBytesReader`*; (c) reject negatives at option time or document them as equivalent to 0.

### F2 — the vouched `*json.UnmarshalTypeError` echoes the caller's numeric literal VERBATIM; the ADR states the opposite as executed fact, and the conditional vouch re-commits the exact structural mistake the re-cut exists to abolish
**Severity:** Major (one DTO field away from Critical — and the bundle's own §6 names that field type)
**Bundle says:** ADR-0186 D2, the three-row decode table — *"| wrong JSON type for the field | `*json.UnmarshalTypeError` | **vouch** — renders the field path and Go types only |"*. Plan §3 phase 4 ships it as code: `if errors.As(err, &ute) || errors.As(err, &se) { err = httpcore.SafeMessage(err.Error(), err) }`.
**The case it misses:** `*json.UnmarshalTypeError` renders "the field path and Go types only" **only when the target field is non-numeric**. When the target is numeric and the literal fails to parse or overflows, `encoding/json` sets `UnmarshalTypeError.Value = "number " + <the caller's literal>` and `Error()` prints it verbatim.
**Evidence:** executed in the worktree, `go test -count=1 -v -run TestVouchedTypeEchoesCallerLiteral ./probefm/...` → `EXIT=0`:
```
body={"n": 41111111111111111111}   vouched(UTE)=true  Error()="json: cannot unmarshal number 41111111111111111111 into Go struct field nums.n of type int"
body={"s": 4111111111111111}       vouched(UTE)=true  Error()="json: cannot unmarshal number 4111111111111111 into Go struct field nums.s of type int32"
body={"f": 1e999}                  vouched(UTE)=true  Error()="json: cannot unmarshal number 1e999 into Go struct field nums.f of type float64"
body={"str": {"4111-…":1}}         vouched(UTE)=true  Error()="json: cannot unmarshal object into Go struct field nums.str of type string"   <- value-free, this is the case the ADR generalised from
```
Reachability today (executed grep over `dto.go`): the only numeric field in any `*Input` type is `ResolveIncidentInput.AddAttempts int`, and it sits on the **discarding** route, so the channel is currently unreachable. `ListInstancesQuery.Limit int` is parsed from the query string, not a JSON body.
**Consequence:** two things. (1) A **false claim stated as executed** in the record's Decision section — Premise Discipline. (2) The vouch is a **closed list keyed on a Go TYPE**, asserting value-freedom of a type the way the abolished exception list asserted it of a sentinel. Spec §6 even writes *"a DTO gaining a `time.Time`, a custom unmarshaller or a `json.Number` changes this, **which is precisely why the opt-in exists**"* — but the decode vouch is **not** an opt-in; it is exactly the closed list that sentence claims was replaced. Adding one `int32`/`float64`/`json.Number` field to any body DTO silently ships verbatim caller digits at 400, with no test and no invariant to catch it. Phase 4 test 7 row 2 (`{"def_ref": 4111111111111111}`) **cannot detect it** — `def_ref` is a string-typed `model.Qualifier`, so it takes the value-free branch.
**Fix:** either (a) do not render `err.Error()`; render a **reconstructed** message from the typed error's structural fields only — `fmt.Sprintf("invalid type for field %s.%s: expected %s", ute.Struct, ute.Field, ute.Type)` — dropping `ute.Value` entirely (this also removes the `*json.SyntaxError` offending-byte concession, since `se.Offset` alone is value-free); or (b) keep `err.Error()` but add a `go/parser`/reflect invariant over the 12 `*Input` types asserting **no numeric-kind field**, so a future DTO change fails the build. Option (a) is strictly better and is one line. Either way, correct the ADR's row: it is not "Go types only".

### F3 — DISCHARGED, recorded so no lens re-derives it: `errors.As` DOES reach `*json.UnmarshalTypeError` / `*json.SyntaxError` through gin's AND fiber's binders — but the rendered TEXT differs across adapters, which the parity phase does not cover
**Severity:** Minor (the assumption discharges clean; the divergence is real but cosmetic)
**Bundle says:** Plan §3 phase 4 — *"`ASSUMPTION (unverified)`: that gin's and fiber's binders preserve those concrete types through `errors.As`. **Test 7 below is what discharges it**"*. Spec §6 lists it as not-executed.
**Evidence:** executed, `go test -count=1 -v -run 'TestFiberBindShapes|TestGinBindShapes|TestStdlibShapes' ./probefm/...` → `EXIT=0`. All three preserve the type:
```
[fiber typemismatch] type=*fiber.BindError  As(UnmarshalTypeError)=true   err="bind \"n\" from body: json: cannot unmarshal string into Go struct field in.n of type int"
[gin   typemismatch] type=*json.UnmarshalTypeError As(UnmarshalTypeError)=true  err="json: cannot unmarshal string into Go struct field in.n of type int"
[stdlib typemismatch] type=*json.UnmarshalTypeError As(UnmarshalTypeError)=true err="json: cannot unmarshal string into Go struct field in.n of type int"

[all three customunmarshal] As(UTE)=false As(SE)=false  -> takes the static branch, as designed
```
⚠ Note fiber v3.4.0 binds in **manual mode by default** (`shouldSkipErrHandling` is true), so `Bind().JSON` does **not** wrap in `*fiber.Error` and does **not** call `ctx.Status(400)` as a side effect. Plan phase 5 lists parity cases for 413, the blanked 403, the correlation-id **shape** and the jsonschema rendering — **no decode-message parity case**, so this ships undetected; and if a phase-5 agent does write one, it fails for a reason unrelated to any decision.
**Fix:** F2's option (a) — reconstruct the message from the typed error's fields — makes the three adapters agree by construction. Otherwise state the divergence in the ADR and in `SECURITY.md`, and add `Bind().Should()` to phase 4's fiber brief.

### F5 — ⭐⭐⭐ D3's at-rest enumeration covers THREE migration files; there is a FOURTH, and the table it creates stores the deployment's authorization policy in the clear
**Severity:** Critical
**Bundle says:** ADR-0186 D3 — *"A test parses **all three** migration files (`internal/persistence/store/migrations/{postgres,mysql,sqlite}`) and asserts that **every column of every table** is classified either `discloses` … or `structural`"*; *"The schema is **9 tables**, and the **table set is identical across postgres, mysql and sqlite**"*; and the harm statement *"a consumer who reads `SECURITY.md`, encrypts the columns we name and leaves the rest in the clear **has been harmed by our documentation**."* Plan §4: *"**at-rest: tables** | ⭐ **9**"*.
**The case it misses:** `find . -name '*.sql'` returns **four** files, not three. The fourth is `internal/authz/casbin/migrations/0001_casbin_rule.sql`, creating a **tenth table** with **seven** free-form columns:

    id    BIGSERIAL PRIMARY KEY,
    ptype TEXT NOT NULL,
    v0..v5 TEXT NOT NULL DEFAULT ''

It is applied by a **module-root public API** — `casbinauthz.MigrateCasbin(ctx, pool)` (`casbinauthz/casbinauthz.go:237` → `internal/authz/casbin/migrate.go:26`), documented as *"Call it … before `NewCasbinAuthorizer(FromDB(...))`"*. `v0`–`v5` are casbin policy tuples: subjects, roles, resource identifiers, and — for this repo's ABAC baseline — **the attribute/process-variable names and comparison values a deployment's predicates are written over**.
**Evidence:** executed —

**Consequence:** three ways, and they compound.
1. `SECURITY.md` is **generated from the classification**, so it will state the plaintext locations and **silently omit `casbin_rule`** — precisely the harm D3's own paragraph forbids.
2. The record is internally inconsistent in a pointed way: ADR-0186 Context §2 blanks the 403 body *because* *"the leaked string is the deployment's own policy source … carrying whatever process-variable and actor-attribute names the deployment's policy names"* — the design treats the policy as sensitive **on the wire** and then omits the table storing that same policy **at rest**.

(c) Correct "9 tables" → "9 in the store schema, plus `casbin_rule` when `casbinauthz.MigrateCasbin` is used".

### F6 — the per-class logging table contradicts itself on 403, and under one of the two readings an ABAC evaluation error becomes UNDIAGNOSABLE: nothing on the wire, nothing in the log
**Severity:** Critical
**Bundle says:** ADR-0186 D2's logging table, rows 1 and 3, in the same table:
| class | logged by default | level |
| 403 | **the raw error** + correlation id — … it belongs in the operator's log | `WarnContext` |
| 400/403 raw error | **only under `httpcore.WithVerboseErrorLogging(true)`, default off** | `WarnContext` |
The same contradiction is restated in plan §3 phase 4 (*"403 raw at `WarnContext`; … the raw 4xx error only under `WithVerboseErrorLogging`"*) and compressed into a single sentence in spec §5 D2×D3 (*"403 logs the raw error …; the raw 4xx error only under `WithVerboseErrorLogging`, default off"*).
**The case it misses:** an implementer has two mutually exclusive instructions for the same class and **both readings are defensible**, so this will be decided by whoever writes the code, not by the record.
- Reading A (403 raw logged by default): the raw 403 error contains the **expr predicate source**, echoed twice (`internal/expreval/expreval.go:135` `%q` + expr's own snippet). D2×D3's whole safety argument is that the fix must not *relocate* disclosure onto `slog.Default()` — and `CustomizeConfig.Logger` defaults to `slog.Default()` (`httpcore/seam.go` `ResolveConfig`). Reading A does exactly the relocation D2×D3 says it prevents.
- Reading B (403 raw behind the default-off flag): today an ABAC **evaluation error** — a broken predicate in the deployment's own policy — is visible only in the 403 response body. `ClassifyError` has no 403 logging at all (`grep`: all three `writeErr`s guard on `status >= 500`). After the change the wire says static `"not authorized"` and the log says nothing. **The operator's only channel for "your policy is syntactically broken" is deleted**, and a bare deny and a broken predicate become indistinguishable.
**Evidence:** reasoned from the quoted rows plus executed source reads (`transport/http/{stdlib,gin,fiber}/write.go` all guard `if status >= 500`; `httpcore` contains no logging call). Not a runtime probe — the behaviour does not exist yet.
**Consequence:** whichever way it lands, one of the two properties the bundle claims is false. Reading A falsifies the D2×D3 "no relocation" resolution; reading B falsifies *"403 stops leaking the deployment's own policy source, **and the fix does not relocate it: the raw error goes to the operator's log**"* (ADR Positive).
**Fix:** decide, and make the table single-valued. The coherent design is a **third** category, because the 403 case is genuinely different from the 400 case: 400's raw error may contain *caller-submitted* values (gate it behind the verbose flag); 403's raw error contains *operator-authored* policy text and no caller input on the eval-error path (log it by default). Say that, delete the overlapping row, and add the falsifier to plan phase 4 test 4: *a test asserting a 403 eval-error IS in the log by default while a 400's raw submitted value is NOT.* As prescribed, test 4 only checks the 400 half.

### F7 — `httpcore.SafeMessage` is unusable by every producer the design asks to opt in, and structural satisfaction gives NO compile-time check — a typo'd method name degrades silently to the safe-looking default
**Severity:** Major
**Bundle says:** ADR-0186 D2 — *"`httpcore` **declares** the interface for documentation and ships `SafeMessage` as the convenience constructor"*, and *"⭐ This is also what makes the two prescribed tests satisfiable … `SafeMessage` is that type"*. Plan §3 phase 1 lists `SafeMessage(msg string, err error) error` as a phase-1 symbol; phases 2 and 3 forbid importing `httpcore` (*"⚠⚠ `runtime/validation` MUST NOT import `transport/http/httpcore`"*, *"⚠ `runtime/kernel` **must not import `transport/http/httpcore`**"*).
**The case it misses:** the two forbidden packages are **two of the three producers that must opt in** (the third, `engine`, is missing entirely — F4). So `httpcore.SafeMessage` is callable only from `httpcore` itself and from the three adapters. Every other opt-in site must hand-roll its own error type implementing the method. Plan phase 2 says so for `runtime/validation`; plan phase 3 does **not** — it says only *"the five static forms **opt in** via `ClientSafeMessage`"*, leaving an implementer to discover that `lister.go`'s plain `fmt.Errorf` forms need a brand-new exported-or-unexported error type in `runtime/kernel`. That is at minimum **three** independent hand-rolled implementations of one interface (validation, kernel, callback-consumer), four if F4 is fixed by adding `engine`.
Then the failure mode: because satisfaction is **structural**, none of those packages can write `var _ httpcore.ClientSafeMessage = (*x)(nil)`. A misspelled method, or a **pointer receiver on a type returned by value** (or vice versa), compiles cleanly and simply fails to satisfy the interface — and deny-by-default turns that into `"invalid input"`, i.e. a *safe-looking, green-tests* silent regression. Phase 2's and phase 3's tests assert their **own package's** rendering, not that `httpcore` picks it up. The only cross-package assertion the plan prescribes is one phase-5 parity case, and it covers **jsonschema only** — not `runtime/kernel`'s five static cursor forms, not `avro`, not the consumer `callback` opt-in.
**Evidence:** reasoned — not executed (the mechanism does not exist yet). The layering constraint and the absence of any compile-time assertion are read from plan §3 phases 1–3 and confirmed by the current import graphs (`runtime/kernel` and `runtime/validation` import no `transport/...` today).
**Consequence:** the delivery's headline mechanism has a failure mode whose signature is *"everything is green and every 400 says `invalid input`"*. That is exactly the shape nobody investigates.
**Fix:** move the interface **and** the constructor into a tiny dependency-free leaf package both layers may import — e.g. module-root `clientsafe` (or `runtime/errsafe`) — and make `httpcore.ClientSafeMessage` a **type alias** to it so the public surface is unchanged. Then every producer writes `var _ clientsafe.Message = (*validationError)(nil)` and a typo is a compile error. If the owner refuses a new package, the minimum is: (a) plan phase 3 must name the new kernel error type explicitly; (b) **each** opt-in producer gets a cross-package assertion — cheapest as a `<pkg>_test` external test file importing `httpcore` (legal: test-only) — and phase 2 test 7's import assertion must then be scoped to the **non-test** import graph (`go list -f '{{join .Imports "\n"}}'`), or it will red on the very test that protects the mechanism.

### F8 — the correlation id makes `TestParity_ErrorEnvelopes`'s byte-for-byte guarantee impossible; the plan never names it, and the obvious repair deletes the guarantee wholesale
**Severity:** Major
**Bundle says:** ADR-0186 D2 — *"**Every error body gains a correlation id** — minted in `writeErr` … (the recording span's id, else a random hex)"*. Plan §3 phase 5 prescribes new parity cases including *"the correlation-id **shape**"*, and describes phase 5's job as *"test fallout"*.
**The case it misses:** `transport/http/parity/parity_test.go:557` already asserts the opposite, deliberately:
```
// TestParity_ErrorEnvelopes verifies that the JSON error envelope
// {"error":"<code>","message":"<text>"} is byte-for-byte identical across all
// three adapters for every error-producing case. These responses contain no
// timestamps, so exact JSON equality is achievable.
```
Three of its four cases run with body parity **on** (`noBodyParity` false): "404 unknown instance", "400 empty JSON body", "404 GET missing instance". Each hits stdlib, gin and fiber as **three separate requests**, so three independently-minted random hex ids. Exact JSON equality becomes unachievable by construction — the id is the **first non-deterministic field ever added to the envelope**, and the test's own comment names determinism as the reason the guarantee exists.
**Evidence:** executed — under the F4 ablation `go test -count=1 ./transport/...` reported `ok github.com/kartaladev/wrkflw/transport/http/parity`, i.e. the suite is green today and will go red purely from D2's id. Source read at `parity_test.go:555-620`.

**Fix:** the plan must make the decision, not the agent: keep byte-for-byte parity over the envelope **with the correlation id redacted** — add a normalisation step to `assertParity` that replaces the id field with a fixed placeholder, plus a separate positive assertion that each adapter emitted a non-empty, well-formed, and **mutually distinct** id. State it as phase 5 work with a named test, and state the falsifier: *it fails against an implementation that omits the id, and against one that emits the same constant for every request.*

### F9 — `ResolveConfig`'s established defaulting idiom, applied to `MaxBodyBytes`, destroys the `0` opt-out; the file's own pattern produces the bug
**Severity:** Major
**Bundle says:** ADR-0186 D1 — *"`httpcore.CustomizeConfig.MaxBodyBytes`, default **1 MiB**, `0` = unbounded (the explicit opt-out)"*. Plan §3 phase 1 symbol list repeats it. Neither says **where** the default is applied.
**The case it misses:** `transport/http/httpcore/seam.go`'s `ResolveConfig` defaults every field **twice** — once before the option loop, once after, as a nil re-check:
```go
cfg := CustomizeConfig[R]{ Wrap: …, InstanceMapper: …, Logger: slog.Default() }
for _, o := range opts { if o != nil { o(&cfg) } }
if cfg.Wrap == nil { cfg.Wrap = … }
if cfg.InstanceMapper == nil { cfg.InstanceMapper = … }
if cfg.Logger == nil { cfg.Logger = slog.Default() }
```
That post-loop pattern exists so a consumer option passing `nil` cannot produce a nil-panic. `MaxBodyBytes` is an `int64` whose **zero value IS the opt-out sentinel**, so the analogous post-loop line — `if cfg.MaxBodyBytes == 0 { cfg.MaxBodyBytes = 1 << 20 }` — silently **clobbers `WithMaxBodyBytes(0)`** and makes the documented opt-out unreachable. Three of three existing defaulted fields use that idiom, so it is the pattern an implementer will copy.
**Evidence:** source read of `transport/http/httpcore/seam.go` `ResolveConfig` (executed read, quoted above). The failure itself is reasoned — the field does not exist yet.
**Consequence:** the opt-out the ADR sells as *the* migration lever, and as the escape hatch for `Negative/costs`' *"Default-on body caps will reject payloads that work today"*, does nothing. A consumer with a legitimate 20 MiB payload has no way out and no error message explaining why.
**Fix:** state it in plan phase 1: *"the 1 MiB default is applied **before** the option loop and there is **no** post-loop re-check — `MaxBodyBytes` is the one field whose zero value is meaningful."* Add a phase-1 test row asserting `ResolveConfig(WithMaxBodyBytes(0)).MaxBodyBytes == 0`, with the falsifier stated: *it fails against an implementation that copies the `Logger` idiom.* (This is the pre-condition for F1's fix; F1 is what happens downstream once 0 survives.)

### F10 — an oversize body that is malformed BEFORE the cap returns 400 on stdlib/gin and 413 on fiber: same request, two statuses, refuting D1's "one policy, one status"
**Severity:** Major
**Bundle says:** ADR-0186 Consequences/Positive — *"The unbounded-body surface closes: **39 sites, one policy, one status**"*. D1 — *"**Oversize is a 413, and the mapping is named rather than assumed.**"* Plan §3 phase 4 test 1 `TestOversizedBodyReturns413` (one fixture, no malformed variant); phase 5 pins a shared 413 parity case.
**The case it misses:** `http.MaxBytesReader` is a **streaming** control — it only fires when the decoder actually reads past the cap. `json.Decoder` stops at the first syntax error, so a body that is oversize **and** malformed early is never read to the cap and surfaces as `*json.SyntaxError` → the 400 arm. Fiber's mechanism is a **pre-parse size check** on `len(c.BodyRaw())`, which fires on size alone. The two mechanisms therefore disagree on exactly the class of request an attacker sends most cheaply: large and garbage.
**Evidence:** executed, `go test -count=1 -v -run TestOversizeButMalformedEarly ./probefm/...` → `EXIT=0`, cap = 1 KiB:
```
wire=   8200  valid, oversize                -> 413 (MaxBytesError)
wire=   8198  malformed at byte 5, oversize  -> 400 (*json.SyntaxError: invalid character 'x' looking for beginning of value)
wire=   8193  malformed at byte 1, oversize  -> 400 (*json.SyntaxError: invalid character '!' looking for beginning of value)
wire=      7  valid, under cap               -> 2xx (accepted)
```
Fiber's prescribed pre-check returns 413 for all three of the first rows (size-only, executed reasoning from `len(c.BodyRaw())`; not run against a live fiber app).
**Consequence:** three concrete harms. (1) A consumer's client-side status switch — which the ADR already breaks once by adding 413 — behaves differently per adapter. (2) The **rejection counter** D1 introduces *"records how often the cap bites"* undercounts on stdlib and gin by exactly the malformed-oversize traffic, which is the traffic an operator most wants counted; the migration story reads that counter. (3) Under F3's `*json.SyntaxError` vouch, the 400 that comes back for an 8 MiB garbage body **renders the offending character**, i.e. the design's one knowingly caller-derived rendering fires on the request class it least wants to be chatty about.
**Fix:** make the mechanism agree — on stdlib and gin, check `req.ContentLength > cap` **before** decoding (cheap, and `ContentLength` is authoritative for non-chunked requests) and fall back to `MaxBytesReader` for chunked/absent-length. Then all three adapters reject on declared-or-observed size first. State in D1 that for **chunked** requests without a `Content-Length` the divergence remains, and add a phase-4 test row `TestOversizeAndMalformedIs413NotBadRequest` per adapter, with the falsifier: *it fails against a `MaxBytesReader`-only implementation.*

### F11 — the widened 4xx logging has NO off switch, so an unauthenticated caller can drive unbounded writes to `slog.Default()`; and the only knob (`WithVerboseErrorLogging`) controls the wrong thing
**Severity:** Major
**Bundle says:** ADR-0186 D2 — *"the entire justification for blanking 403 … rested on a join nobody built. **The guard widens**"*, with a per-class table logging 400, 403 and 413 at `WarnContext` **by default**. `Negative/costs` lists only: *"`Logger` also starts receiving 400/403/413 records, changing log volume."*
**The case it misses:** the only new option is `WithVerboseErrorLogging(bool)`, default off, and it gates the **raw error**, not whether a record is written at all. So after this delivery there is **no configuration** in which a 4xx produces no log line. `CustomizeConfig.Logger` defaults to `slog.Default()` (`httpcore/seam.go` `ResolveConfig`), and admin routes are documented as having *"NO built-in authentication"* (`groups.go:204/209` in gin/fiber), so the reachable surface includes routes an anonymous caller can hit. A caller sending malformed JSON at line rate produces one `WarnContext` per request, synchronously, on the request path — with no sampling, no rate limit, and no way for the consumer to turn it off short of `WithLogger(slog.New(discardHandler))`, which also discards the 5xx records they need.
**Evidence:** reasoned from the bundle text plus executed source reads: all three `writeErr` implementations currently guard `if status >= 500` (`transport/http/{stdlib,gin,fiber}/write.go`), and `httpcore` contains no logging call at all — so today the 4xx log volume is exactly **zero** and this is a 0→N change, not an N→M change. Not load-tested.
**Consequence:** on a public-facing mount, 4xx log volume becomes attacker-controlled. In a shipped library that is a denial-of-service amplifier against the consumer's log pipeline and its bill, introduced by a security fix, and the `Negative/costs` bullet frames it as "changing log volume" rather than "attacker-controlled volume".
**Fix:** add a genuine control and name it in D1/D2 and `SECURITY.md`: either `WithErrorLogging(minStatus int)` (default 400, set 500 to restore today's behaviour) or a per-class enable set. Also state the level explicitly per class rather than "all `WarnContext`" — a routine 400 at `Warn` is what floods; `Debug` for 400 and `Warn` for 403/413 is the defensible split, and it does not weaken the 403 join. And add a `Negative/costs` bullet saying the volume is caller-driven.

### F12 — fiber's mount-time WARN is the sole mitigation for a documented silent divergence, and it sits in a function the documented admin path never calls; it is also keyed on a constant rather than the app's actual limit
**Severity:** Major
**Bundle says:** ADR-0186 D1 — *"Fiber's `Mount` therefore **logs a WARN at mount time** when `MaxBodyBytes > fiber.DefaultBodyLimit`, and `SECURITY.md` records the divergence."* Plan §2 map row: *"D1 fiber mount **WARN** above `DefaultBodyLimit` | 4 | `fiber`"*.
**The case it misses:** two independent holes.
1. **`Mount` is not the mount path for admin routes.** `transport/http/fiber/mount.go:15` mounts only Instance/Task/Message; its own godoc says *"For more control — e.g. **admin routes** … call each RouteGroup's `Customize` method directly."* `AdminRoutes.Customize` (`fiber/groups.go:222`) never calls `Mount`. The repo's own reference wiring already takes that path — `examples/production_wiring/main.go:274` calls `stdlib.AdminRoutes{Svc: svc}.Customize(adminMux, …)` directly, mounting admin on a **separate** mux. So the consumer most exposed to the divergence — the one mounting the admin surface, which is where all three discarding decode sites live — is the one guaranteed not to see the WARN. Same for `MountHealth`.
2. **It compares against the wrong quantity.** `fiber.DefaultBodyLimit` is a package **constant** (4 MiB), not the app's configured limit, and `Mount` receives a `fiberlib.Router` **interface**, not a `*fiber.App`, so the real value is unreadable. Consequence: the WARN is a false positive for a consumer who already raised `fiber.Config.BodyLimit` (the ADR concedes this), **and is silent for the far more likely case** — a consumer who *lowered* it. `fiber.Config.BodyLimit = 256 * 1024` with the shipped **default** `MaxBodyBytes = 1 MiB` produces exactly the documented divergence (framework plain-text 413, no `ErrorBody`, no id, no log) with `1 MiB < 4 MiB`, so no WARN fires.
**Evidence:** executed source reads — `transport/http/fiber/mount.go` (full file, quoted above), `transport/http/fiber/groups.go:212-222` (`AdminRoutes` + its own `Customize`), `transport/http/fiber/options.go:8` (the documented two-step assembly), `examples/production_wiring/main.go:274`.
**Fix:** move the check out of `Mount` into the shared per-group path every fiber group already runs — i.e. emit it from `Customize`/`ResolveConfig`-time in each fiber route group, guarded by a `sync.Once` per config so it is not emitted five times. And change the predicate: warn whenever `MaxBodyBytes > fiber.DefaultBodyLimit` **or** unconditionally record one INFO line naming both numbers, since the app's real limit is unknowable — an operator can then compare. Update the plan's phase-4 fiber brief accordingly; as written it names `Mount` specifically.

### F13 — `SECURITY.md` is "generated from the classification", but nothing names the generator, the command, or a drift check; and the invariant test cannot see the document
**Severity:** Major
**Bundle says:** ADR-0186 D3 — *"The `SECURITY.md` list is **generated from that classification**, so the document and the test **cannot disagree**."* Plan §3 phase 6 repeats it; plan §3 phase 7 says *"the at-rest posture, over the **generated** column list (D3). ⚠ Do not hand-write it."*
**The case it misses:** the plan's phase table assigns phase 6 (`internal/persistence/store`, the invariant) to one agent and phase 7 (docs) to the controller — **different phases, different actors, and no artifact passes between them**. No `//go:generate` directive is named, no generator symbol is named, no command appears in the Verification checklist (§5 lists `go test`, `golangci-lint`, `go vet`, `go build ./examples/...` — nothing that regenerates or diffs `SECURITY.md`). So "cannot disagree" is not a property of the design; it is an aspiration. The classification lives in a Go test file in an `internal/` package and `SECURITY.md` lives at the repo root; a future column addition makes the **test** red (good) and leaves `SECURITY.md` stale (silent) once someone fixes the test without regenerating.
**Evidence:** reasoned — read across ADR D3, plan §3 phases 6 and 7, and plan §5. `grep -rn "go:generate"` over the repo finds mockgen directives only; there is no doc-generation precedent to inherit.
**Consequence:** the one deliverable of D3 is a document, and its stated correctness mechanism does not exist. Given the enumeration has rotted three times, a fourth rot lands directly in the file a consumer reads to decide what to encrypt — the exact harm D3 opens with.
**Fix:** make the document a **test fixture**, which is the only shape that cannot drift: the classification test **renders** the markdown section and compares it against the committed `SECURITY.md` block (golden-file style, `-update` flag to regenerate). Then a new column fails phase 6's test *and* the document test, and regeneration is one command. Name that test in plan phase 6 (`TestSecurityMdMatchesClassification`), name the `-update` flag, and add the regeneration command to §5's checklist. Also state which side wins on mismatch.

### F14 — `doc.go:66` documents `ClassifyError` as "(5xx redaction)"; after D2 it redacts 4xx too. The plan corrects one godoc and misses this one
**Severity:** Minor
**Bundle says:** ADR-0186 D2 — *"Changing that signature breaks an exported function `doc.go:66` advertises as a consumer seam"*, and *"`CustomizeConfig.Logger`'s godoc — *"receives 5xx raw error details (never sent to clients)"* — is corrected in place."* Plan §2 map has a row for the `Logger` godoc; none for `doc.go`.
**The case it misses:** `doc.go:66` reads `//     ClassifyError (5xx redaction), Instrumentation.Observe (static route template),`. The record cites that exact line to justify **not** changing the signature, then leaves the description it contains false: after D2, `ClassifyError` redacts 403 unconditionally and 400 by default. A consumer reading the module's front-door doc comment is told 4xx messages pass through.
**Evidence:** executed — `sed -n '55,80p' doc.go` shows the line verbatim at 66; citation confirmed accurate, content confirmed about to become wrong.
**Consequence:** the module-root doc, which is the first thing a library consumer reads (CLAUDE.md: *"the product is the module-root public API"*), misdescribes the delivery's central behaviour change.
**Fix:** add a plan §2 row and a phase-7 bullet: `doc.go:66` → `ClassifyError (4xx/5xx body redaction)`. While there, sweep the same paragraph for the admin-routes sentence, which stays true.

### F15 — the at-rest invariant lands in a Docker-bound package for no reason, and `MaxBytesReader` is handed a wrapper it cannot use
**Severity:** Minor (two small operational notes, recorded together)
**(a) Phase 6 placement.** Plan §1 and §3 phase 6 state the Docker requirement accurately (*"≥5 container-bound test files"* — verified: `ls internal/persistence/store/*_test.go` = 38 files, `grep -l 'dbtest\|testcontainers'` = **17** of them; there is **no `TestMain`**, so the package compiles and a name-filtered run works without a daemon). But the new test **only reads `.sql` files** and has no reason to live there. Putting it in a leaf package — e.g. `internal/persistence/store/migrations` with its own `//go:embed`, or a `migrationsaudit` package — makes the delivery's only Docker dependency disappear, and lets a contributor without a daemon run the invariant that exists to catch their column addition. CI is unaffected either way (`.github/workflows/ci.yml:63` runs `go test -race ./...` on a runner with Docker).
**(b) `MaxBytesReader`'s `w` argument.** stdlib handlers receive `*statusRecorder` (`transport/http/stdlib/observe.go`), and gin handlers receive `gin.ResponseWriter`. `http.MaxBytesReader` type-asserts its `w` for the unexported `requestTooLarger` hook **without** consulting `Unwrap()`, so neither wrapper matches and the connection is not marked close-after-reply on an oversize request. Bounded and harmless (net/http drains at most 256 KiB before closing), but it means the two adapters differ from bare `net/http` in connection reuse after a 413, and any future load measurement of the cap will see it. Worth one sentence in D1 rather than a surprise. `statusRecorder` already has an `Unwrap()` for `http.NewResponseController`; passing `rw.Unwrap()` to `MaxBytesReader` restores the hook on stdlib.
**Evidence:** executed file counts and greps as quoted; `transport/http/stdlib/observe.go` read in full. The `requestTooLarger` behaviour is read from the `net/http` source contract, not probed.

### F16 — the 413 log row demands "the observed size", which is UNOBTAINABLE on stdlib and gin: `http.MaxBytesError` carries only `Limit`. Phase 4 test 5 is prescribed for all three adapters and can pass on only one
**Severity:** Major
**Bundle says:** ADR-0186 D2's per-class logging table — *"| 413 | the **observed size** + the cap + correlation id | `WarnContext` |"*. Spec §5 D1×D2 (iii) presents this row as the resolution of an author interaction finding: *"✅ (iii) 413 has its own logging row (**observed size** + cap + id). ⚠ **(iii) was missing from the six-decision bundle** and is an author interaction finding of this re-cut."* Plan §3 phase 4 test 5: *"`TestOversizeIsLoggedWithSizeAndCap` — the 413 logging row"*, listed under **"Tests per package"** for all three parallel agents.
**The case it misses:** `http.MaxBytesReader` exists **precisely so the oversize body is never fully read**, so the true size is never known, and the error type reflects that — it has exactly one field. The observed size is knowable only on fiber, whose pre-check reads `len(c.BodyRaw())` on an already-buffered body.
**Evidence:** executed, `go test -count=1 -v -run TestMaxBytesErrorFields ./probefm/...` → `EXIT=0`:
```
http.MaxBytesError fields: Limit int64;
wire bytes actually sent=9008  mbe=http: request body too large  mbe.Error()="http: request body too large"
```
9008 bytes were sent; the error reports only the 1024 limit.
**Consequence:** two of the three phase-4 agents receive a prescribed test they cannot satisfy. The likely outcomes are both bad: an agent logs `Limit` under the attribute name `size` (a **false log field** — the operator reads it as the request's size and sizes their cap from it), or an agent quietly drops the attribute and the three adapters' 413 records diverge with nothing asserting it. This also compounds F10: on stdlib/gin the log cannot distinguish "8 KiB over a 1 KiB cap" from "8 GiB over a 1 KiB cap", which is exactly the signal an operator needs to decide whether they are being attacked.
**Fix:** change the row to what is actually available and make the asymmetry explicit — `cap` + correlation id on all three, plus `observed_bytes` **on fiber only**, or on stdlib/gin `content_length` (from `req.ContentLength`, **labelled as caller-declared and `-1` for chunked**, never as an observed measurement). Alternatively adopt F10's fix — a `req.ContentLength` pre-check — which makes a declared size available at the rejection point on all three, still caller-supplied and still needing that label. Then split phase 4 test 5 into a shared assertion (cap + id present) and a fiber-only assertion (real size), and say so in the brief so three parallel agents do not each invent a different answer.

The counting lens's standing lesson ("the failure was the grep's NET") generalises here from enumerations to **scopes**.
